# Integração Cloudflare R2

> Status: preparado
> Owner: integrations/media
> Última revisão: 2026-09-07

## Propósito

Armazenar conteúdo binário separado do PostgreSQL. Banco mantém identidade, relações, provenance e metadados; R2 mantém objetos.

R2 é a camada de mídia/conteúdo do TDA, não o filesystem genérico do aplicativo. Assets críticos e pequenos que fazem parte do shell do site podem permanecer versionados no Git quando isso reduz dependência externa e melhora auditabilidade.

## Buckets documentados

- `tda-media-public` — 22 imagens verificadas e entrega HTTPS ativa em `media.dnd.faysk.dev`; consumo pelo site aguarda release restrita e promoção das referências;
- `tda-media-private` — privado;
- `tda-media-preview` — privado e isolado de production.

Nome `public` não autoriza conteúdo automaticamente. O bucket pode continuar privado até a política de entrega pública estar pronta.

## Regra de placement

### Permanece no Git/runtime

Por padrão permanecem em `public/brand` ou outra pasta versionada do app:

- favicon e ícones críticos do shell;
- SVGs oficiais pequenos da marca;
- manifest/PWA assets necessários no bootstrap do site;
- arquivos pequenos que precisam acompanhar exatamente uma versão do código;
- assets cuja integridade é protegida por checksum/CI.

O Brand Pack oficial continua sendo governado por `docs/design-system/official-assets.md`.

### Vai para `tda-media-public`

Conteúdo público e cacheável que não precisa estar acoplado ao deploy do app:

- cover/hero/gallery de sessões;
- retratos e artworks de entities publicados;
- mapas e imagens narrativas publicadas;
- cards sociais gerados/derivados quando não fizerem parte fixa do bundle;
- derivados raster otimizados de conteúdo.

### Vai para `tda-media-private`

- masters/originais que não são runtime público;
- uploads ainda não aprovados;
- material editorial/review;
- fontes de geração e arquivos de trabalho;
- arquivo de segurança do Brand Pack oficial, quando importado para R2;
- qualquer binário cuja audience não seja explicitamente pública.

### Vai para `tda-media-preview`

- homologação;
- testes de upload/derivação;
- assets temporários de Preview;
- conteúdo que ainda não foi promovido para production.

Preview nunca deve usar objeto real de production apenas por conveniência.

## Modelo de chave

A chave do objeto deve ser previsível, estável e baseada em identidade canônica. Filename humano não é identidade.

### Sessões públicas

```text
campaigns/{campaign-slug}/sessions/{session-uuid}/cover/{content-hash}.{ext}
campaigns/{campaign-slug}/sessions/{session-uuid}/hero/{content-hash}.{ext}
campaigns/{campaign-slug}/sessions/{session-uuid}/gallery/{content-hash}.{ext}
```

### Entities públicas

```text
campaigns/{campaign-slug}/entities/{entity-uuid}/portrait/{content-hash}.{ext}
campaigns/{campaign-slug}/entities/{entity-uuid}/artwork/{content-hash}.{ext}
campaigns/{campaign-slug}/entities/{entity-uuid}/gallery/{content-hash}.{ext}
```

### Conteúdo de site

```text
site/social/{asset-name}/{content-hash}.{ext}
site/shared/{asset-name}/{content-hash}.{ext}
site/generated/{asset-name}/{content-hash}.{ext}
```

### Privado

```text
brand/official-pack/{version}/...
campaigns/{campaign-slug}/sessions/{session-uuid}/originals/{content-hash}.{ext}
campaigns/{campaign-slug}/entities/{entity-uuid}/originals/{content-hash}.{ext}
uploads/pending/{object-uuid}/{content-hash}.{ext}
uploads/review/{object-uuid}/{content-hash}.{ext}
```

O hash no filename serve para imutabilidade/cache e deduplicação operacional. O banco continua dono da relação semântica entre sessão/entity e objeto.

## Identidade, metadados e provenance

O banco deve registrar informação suficiente para localizar e auditar o objeto sem transformar path em entidade de domínio.

Para mídia gerenciada pelo reboot, registrar conforme o contrato de domínio permitir:

- bucket;
- object key;
- MIME type;
- tamanho;
- hash criptográfico;
- origem/provenance;
- audience/visibilidade;
- timestamp de importação;
- relação com a entidade/sessão canônica;
- variante funcional (`cover`, `hero`, `portrait`, `gallery`, etc.).

URLs públicas são endereço de entrega, não identidade permanente do objeto.

## Credenciais

A credencial de produção deve ter escopo mínimo aos buckets necessários. Nunca usar credencial administrativa ampla no app.

Secrets permitidos somente em:

- server/worker autorizado;
- secret manager/env apropriado;
- companion quando houver contrato específico e escopo mínimo.

Nunca em:

- código Git;
- documentação;
- browser bundle;
- screenshot/log público.

## Separação de ambientes

Preview usa bucket próprio e não recebe automaticamente credencial de production. Testes não devem escrever em objetos reais apenas porque o código é o mesmo.

## Público e entrega

Quando mídia pública for liberada:

- conteúdo precisa estar explicitamente aprovado para audience pública;
- MIME/origem devem ser validados;
- objetos publicados devem ser tratados como imutáveis sempre que possível;
- cache headers devem ser definidos por classe de asset;
- substituição de conteúdo deve gerar nova key/hash em vez de sobrescrita silenciosa;
- remoção/retcon deve possuir estratégia de invalidation quando aplicável.

Custom domain/CDN público só deve ser ativado depois que o bucket estiver populado e validado. `media.tda.faysk.dev` é um candidato de naming, não uma configuração vigente.

Estado operacional de 2026-09-07: o domínio escolhido e validado é **`media.dnd.faysk.dev`**, limitado ao bucket público. O domínio principal do site não mudou; `r2.dev` permanece desativado e private/preview não receberam domínio público. Evidências e plano de promoção estão no [reparo e entrega pública](media-public-delivery-2026-09-07.md). Os snapshots de recuperação anteriores continuam históricos.

## Privado

Entrega de mídia privada deve ocorrer apenas após authorization. URL assinada é mecanismo temporário de acesso, não substitui a verificação de permission.

Nenhum bucket privado vira fallback público quando uma autorização falhar.

## Áudio

Decisão do reboot: **não reter áudio bruto na cloud como requisito**.

R2 pode guardar binários aprovados/necessários, como imagens e futuramente derivados de áudio, mas o companion local continua dono do processamento pesado e retenção bruta deve seguir política explícita.

## Migração do legado

Imagens ainda publicadas em origens legadas permitidas podem continuar funcionando durante a transição. Isso não significa que os buckets novos já estejam populados nem que a origem antiga seja arquitetura final.

O inventário observado em 2026-09-07 está registrado em `media-inventory-2026-09-07.md`.

Processo obrigatório de migração:

1. inventariar objeto/origem e consumidor atual;
2. confirmar identidade canônica (`campaign`, `session`, `entity`) e audience;
3. baixar/capturar o binário sem transformação destrutiva;
4. verificar hash, MIME, tamanho e dimensões quando aplicável;
5. escolher a key canônica no bucket correto;
6. copiar para R2;
7. ler o objeto de volta e verificar integridade;
8. atualizar referência no banco sem remover imediatamente a provenance antiga;
9. validar frontend desktop/mobile e metadata social quando aplicável;
10. confirmar rollback;
11. somente então considerar remover dependência/origem antiga.

Nunca apagar a origem antes de validar o novo caminho de entrega.

### Recuperação executável da issue #25

`tools/migrate-session-media-r2.mjs` recupera somente as 22 imagens históricas de `yuhara-main`, a partir do inventário revisado em `tools/media/session-image-sources.json`. GitHub usa o commit imutável `48f8a43e8145e782d3bf4186a4a9b4218a92c643`; as URLs originais permanecem como provenance. O relatório datado está em [recuperação validada](media-recovery-2026-09-07.md).

Node 24 e `pnpm install --frozen-lockfile` são pré-requisitos. A decodificação completa usa o Sharp já instalado como dependência opcional do Next; instalação sem dependências opcionais falha explicitamente. Não há nova dependência ou serviço. Executar na raiz do clone:

```powershell
# Padrão: download público, hash, decodificação e preservação local. Sem R2/banco.
node tools/migrate-session-media-r2.mjs

# Dry-run operacional: revalida as 11 associações no banco e faz HEAD no R2.
# O env local existente é lido diretamente; não copiar nem imprimir seus valores.
node --env-file=D:/Projects/tda/.env.local tools/migrate-session-media-r2.mjs --verify-db --check-r2

# Testes sintéticos, sem rede ou credenciais.
node --test tools/media/recovery.test.mjs
```

`--output <diretório>` seleciona a pasta local; o padrão é `.local/session-media`, ignorada pelo Git. `originals/{sha256}.{ext}` preserva os bytes; `manifest.json` registra a execução, com checkpoint após cada objeto. Reexecutar baixa e compara novamente, sem sobrescrever um original divergente. Interrupção durante a criação local pode deixar arquivo incompleto: a próxima execução aborta por colisão; preservar esse diretório e usar outro `--output` para repetir, sem apagar evidência. Usar diretórios de saída distintos para execuções concorrentes.

O inventário fixa SHA-256, tamanho, MIME e dimensões medidos. Mudança na origem ou associação de banco exige nova revisão do inventário; não atualizar hashes automaticamente para contornar uma falha. MIME e extensão vêm dos bytes decodificados: as duas imagens de 29/07 são PNG apesar da URL `.webp` e do header HTTP incorreto. Seus destinos terminam em `.png`; as outras 20 permanecem `.webp`. Nenhum original é recomprimido.

O comando abaixo está **implementado para uma etapa futura, não executado nem autorizado nesta rodada**:

```powershell
node --env-file=D:/Projects/tda/.env.local tools/migrate-session-media-r2.mjs --verify-db --upload
```

Upload exige flag explícita e revalidação do banco. A única escrita remota implementada é `PutObject` em `tda-media-public`: `HeadObject` antes; divergência de tamanho/MIME/metadata SHA-256 aborta; igualdade exige ainda `GetObject` e hash dos bytes para skip. Objeto ausente recebe PUT condicionado a `IfNoneMatch: *`, fechando a corrida HEAD/PUT. Uma resposta 403 ou bucket inexistente nunca é tratada como objeto ausente; colisão/precondition failure nunca provoca retry incondicional. Depois do PUT, GET valida MIME, bytes e SHA-256. A compatibilidade segue a [API S3 do R2](https://developers.cloudflare.com/r2/api/s3/api/) e suas [operações condicionais](https://developers.cloudflare.com/r2/api/s3/extensions/).

As credenciais R2 existentes são lidas somente com `--check-r2` ou `--upload`; o bucket é fixo e deve coincidir com `R2_PUBLIC_BUCKET`. `--verify-db` usa somente SELECT das identidades, datas e referências públicas das sessões. Erros externos não são serializados; falhas por objeto registram identidade, fase e código sanitizado. O processo aborta na primeira falha, mantendo checkpoints e originais; não há SQL de escrita, delete, publicação, DNS ou deployment.

Rollback desta etapa é manter referências existentes. Mesmo um upload verificado é aditivo; não autoriza trocar referências nem remover origens. Upload remoto real, interrupção remota real e entrega pública continuam pendentes; testes de PUT/GET usam um cliente sintético.

### Contrato de imagem pública validada para metadata

O manifesto distingue `verificationStatus=local-verified` de `r2-readback-verified`. Nenhum dos dois comprova acesso público. `visibility=public-intended` é a intenção editorial; não é ACL ou evidência de publicação. Nesta recuperação, `publicUrl=null` e `publicDeliveryStatus=not-verified` em todas as linhas, inclusive se uma futura execução verificar o objeto via S3 autenticado.

A camada central de metadata da #47 deve consumir apenas uma referência cuja **entrega pública** tenha sido validada previamente por operação controlada (GET HTTPS sem autenticação, decodificação/MIME/hash correspondente), associada a `sessionId`, `role`, `sha256`, URL exata e data de verificação. Essa validação futura produz um registro distinto; este script não o promove. Não promover o `resolvedSourceUrl` de recuperação automaticamente como URL editorial.

URL HTTPS sintaticamente válida, nome de bucket público e hash na key não bastam. Na ausência dessa evidência, usar o fallback oficial `/og/default` do helper central, sem HEAD/fetch remoto por request. As 12 URLs históricas confirmadas como 404 permanecem inelegíveis até nova validação de entrega. O helper pertence à frente de metadata; a recuperação fornece o manifesto e não duplica essa lógica.

## Cache e versionamento

- objetos públicos com hash na key podem receber cache longo/imutável;
- conteúdo mutável não deve reutilizar key imutável;
- masters privados não dependem de cache público;
- metadata no banco pode apontar para uma versão nova sem destruir a versão anterior imediatamente;
- mudanças de formato (`png` -> `webp`, por exemplo) são derivados e devem preservar provenance do original.

## Observabilidade e auditoria

Mudança de mídia relevante deve deixar evidência suficiente para responder:

- de onde veio;
- quem/qual processo promoveu;
- para qual bucket/key foi;
- qual hash foi validado;
- qual registro do banco passou a referenciar o objeto;
- se a origem antiga ainda existe;
- como fazer rollback.

Snapshots de inventário são auditorias datadas, não fonte canônica do estado dinâmico.

## Failure modes

- objeto ausente: não apagar metadata automaticamente;
- upload parcial: não promover referência como ativa antes de confirmação;
- credencial inválida: falha explícita, sem fallback para bucket público;
- path duplicado: usar estratégia de key/version/hash;
- hash divergente após upload: tratar como falha de migração;
- acesso público acidental: tratar como incidente de segurança;
- referência de banco atualizada antes do objeto estar validado: rollback para referência anterior;
- origem antiga indisponível: não substituir por placeholder silencioso sem decisão de produto.

## Custos

Infra atual foi desenhada para permanecer em franquias gratuitas/Hobby quando possível, mas gratuidade não é garantia de custo zero. Monitorar volume/requests antes de features de mídia pesada.

Não habilitar Cloudflare Images, Stream, Infrequent Access ou outra classe/serviço pago apenas por conveniência sem decisão explícita.
